# S-002 database handoff

Use Supabase Postgres with Prisma for server persistence. No `psql` installation is required. Set server-only `DATABASE_URL` in `apps/api/.env` using the Supabase Connect **Session pooler** connection (port 5432), then run `pnpm --filter @kayda-sathi/api db:apply`. The runner applies the authoritative SQL migrations in a transaction, records checksums, and skips unchanged applied migrations. Alternatively, run the SQL in Supabase Dashboard → SQL Editor. Do not run both methods on an already-created schema without baselining its migration history.

Generate the client with `pnpm --filter @kayda-sathi/api db:generate`. SQL migrations remain the source of truth for RLS, storage, auth foreign keys and triggers; Prisma maps the ten application tables. Do not use `prisma db push` to replace this schema. The API uses parameterized Prisma queries and transactions, with explicit ownership checks because its privileged connection bypasses browser RLS. If using a dedicated Prisma role, grant access to application tables and `public.save_draft(uuid,integer,text,text)`; follow Supabase's Prisma connection guide. Schema application also needs privileges on the referenced Supabase auth/storage objects: use a migration-capable admin Session connection via optional `MIGRATION_DATABASE_URL` when the runtime Prisma role lacks those privileges. The runner otherwise uses `DATABASE_URL`.

Run `pnpm --filter @kayda-sathi/api test` for local PostgreSQL regression checks. The embedded PostgreSQL engine supplies minimal Supabase auth/storage schemas and executes the actual migration and rollback ownership script; it needs neither Docker nor a hosted database. It checks SQL policies and application behavior, but does not substitute for hosted Supabase Auth/Storage and real concurrent-client integration checks.

The migration implements the ten PRD tables, ownership RLS, private `case-evidence` storage, immutable original accounts, ledger-driven case revisions, plan revision uniqueness, and draft regeneration versions separate from `save_token`.

Migration 002 makes browser fact access read-only; all fact edits use revision-checked API mutations. Superseded facts are retained using `retired_at`, with current values filtered by the API. Browser clients can edit checklists and only read generated plans, drafts, updates and document analysis. AI request metadata has no client privileges or text payload columns. Feedback and document references cannot cross cases.

`commit_plan` is service-only and atomically checks owner/revision/deletion, requires confirmed facts and no disputed facts, reserves the request UUID, inserts the immutable plan, and advances the current revision. Validate the complete shared output schema, claim IDs and safety rules in the API before calling it. Map unique request violations to HTTP 409 and `STALE_CASE` to HTTP 409. No AI response is retained in request logs.

`lock_case_revision` remains a service-only RPC building block. Calling it in a separate HTTP transaction does **not** protect a later write. `Store.execute` reserves request UUIDs before inference; `Store.commit` locks the case, compares revision/deletion and atomically commits validated output plus request status. No inference call holds a database transaction open. Stale/errors retain metadata only; successful hard deletion removes that case's metadata too.

Authenticated editors call `save_draft(draft_id, expected_token, body, status)` and retain their unsaved text on `DRAFT_CONFLICT`. Regeneration inserts a new version rather than overwriting the edited draft. Sent or non-current drafts cannot be saved through this RPC.

Deletion authenticates in the API, marks the case hidden, recursively removes storage objects using the service role, then hard-deletes the case and children. Cleanup failure retains the hidden row for retry. New storage writes require flat `user/case/UUID` paths and take a parent SHARE lock so deletion cannot pass an approved upload transaction. Historical nested objects are still cleaned recursively. Client hard deletion is disabled. Hosted Storage transaction/race behavior still needs integration validation.
